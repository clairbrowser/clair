# The native window

Clair's browser windows are native AppKit and SwiftUI, built by `ClairUI`, while Chromium keeps the browser behind them: tabs, navigation, sessions, profiles, extensions and its own dialogs. This page describes how the two halves meet, where each piece lives, and how to add a hook when a Chromium surface misbehaves in the native window. The full reasoning is in the `replace-browser-window` change's `design.md` (D1–D17), archived under `openspec/changes/archive/` once it ships.

## Architecture

```
Chromium (engine)                                   ClairUI (Swift)
──────────────────────────────────────────          ─────────────────────────────
Browser ── BrowserWindow ─▶ ClairBrowserWindow       BrowserWindowController
                              │  owns                  │  ClairWindow
                              ▼                        │
                           ClairNativeWindow (NSWindow) ◀── styled and filled by ClairUI
                              │
                           ClairChromiumBrowser ──── ClairBrowser ────▶ (calls in)
                              (Objective-C bridge)  ◀── ClairWindow ──── (pushes out)
```

- **Chromium keeps the browser (D1).** `ClairBrowserWindow` implements Chromium's `BrowserWindow` for normal browsers. Each of its methods is forwarded to `ClairUI`, answered from the `NSWindow`, handled by a helper in the overlay (location bar stub, find, full screen, modal dialog host, extensions container, status, docked DevTools), or belongs to a feature the native window doesn't have, in which case it does nothing and logs once ("Clair: … isn't available in the native window").
- **Every normal window is native while `ClairUI` runs (D2).** `browser_window_factory.cc` asks `clair::CreateNativeBrowserWindow` first. Pop-ups, app windows, Picture-in-Picture, undocked DevTools, the profile picker and the task manager stay Chromium's. Without `ClairUI.framework` (the bare engine in CI's smoke test) Chromium builds its own window. With the framework present but failing to load, Clair shows an alert and quits.
- **The contract is `native/ClairHost.h` (D3).** `ClairBrowser` is Chromium's side (tabs, commands, autocomplete sessions, downloads, extension actions), `ClairWindow` is `ClairUI`'s (callbacks for changes, the command bar, find, toasts, anchors for Chromium's bubbles). Chromium pushes immutable snapshots, coalesced to one per run-loop turn per tab; Swift never holds a C++ pointer. The header is an engine input: changing it changes the engine key and needs an engine build.
- **Closing goes through Chromium.** The close button calls `requestClose`, which runs Chromium's `beforeunload` flow; the `NSWindow` closes only when Chromium calls `BrowserWindow::Close`.

## Spaces

The archived `add-spaces` change's `design.md` (`openspec/changes/archive/2026-11-12-add-spaces/`) has the reasoning (D1–D11).

- **The Space store (D1).** `ClairSpaceStore` keeps the Spaces in Chromium's Local State (`clair.spaces`, and `clair.last_space` for the Space a new window shows). It creates "Home" when none is stored and refuses to delete the last Space. `clair::RegisterLocalStatePrefs` registers both prefs from `browser_prefs.cc`. Each Space is a record with its own sort key, `order`, and the Spaces are sorted by it, then by ID, so moving one rewrites only its record (`add-tab-folders` D12); the keys come from `clair_order_key.{h,mm}` (see Pins and favorites below). A Space saves its profile by the ID of `clair.profiles` (see Profiles below).
- **The tab lists (D2).** `ClairSpaceTabs`, one per profile (kept as the profile's user data), observes the tab strip of every native window of the profile and keeps one ordered list of tab handles per Space, across windows: its Today tabs. A tab bound to a pinned tab or favorite is in no list (see Pins and favorites below). Each tab carries its Space as `WebContents` user data. A new tab joins the Space its window shows, a restored one its saved Space at its saved place, and a Peek its parent's. The tab strip's order no longer means anything to the user, except that a Peek follows its parent. An incognito or guest profile has one Space of its own, which isn't in the store. `ClairSpaceTabs` also owns the tab snapshots and pushes each Space's list and each tab's changes to the host's `ClairSpacesObserver`, once per run-loop turn, before a window hears that its active tab changed.
- **The shown Space (D3, D4, D5).** Each `ClairBrowserWindow` shows one Space, and its active tab always belongs to it: when another tab becomes active for any reason, the window shows that tab's Space. Showing a Space activates the tab last active in it in that window, or opens a new tab page with the command bar. The window also keeps the tab the user came from and picks the next tab before a close Clair starts (that tab, else the row above, else the row below, over the open pinned tabs and then the Today rows; a favorite counts as came-from but isn't a row), or, for a page with unload handlers, once the page agrees to close (`ClairBrowserWindow::BeforeUnloadFired`). It runs the tab commands (Cmd+number, Next and Previous Tab, Ctrl+Shift+PageDown and PageUp, Close Tabs Below, Close Other Tabs) over its rows of the shown Space: every pinned tab, open or not (landing on one that isn't opens it), then the Today rows; PageDown and PageUp move a row within its own section, or its folder. A closed folder's pinned tabs are rows only while their page is open, as the sidebar lists them (`RowPins`, `add-tab-folders` D9).
- **Sessions (D6).** Each tab's Space and its index in the Space's list ride in its session extra data (`clair_space`, `clair_order`), so session restore and Reopen Closed Tab put it back. Session restore always runs, whatever `session.restore_on_startup` says (see Pins and favorites below, D12); which windows come back is the restore setting's (see Profiles below).
- **`ClairUI` (D10).** `SpacesModel`, one per host, holds the Spaces and each Space's tabs; each window copies its shown Space's list into its `BrowserWindowModel`. The sidebar's content between the URL field and the footer is a pager that slides between Spaces.

## Tabs shared across windows

The archived `share-tabs-across-windows` change's `design.md` (`openspec/changes/archive/2026-11-13-share-tabs-across-windows/`) has the reasoning (D1–D5). Every tab still lives in one real browser; what changed is which rows a window lists and what happens when it selects a row another browser holds.

- **One list (D1).** A regular window lists its shown Space's whole list, whichever browser holds each tab; an incognito or guest window lists its own tabs, by `browserID`. `ClairBrowserWindow::Rows()` and the tab commands work over that list, and the bridge accepts any listed tab of the profile in its commands (`rowTabWithID:`).
- **Take (D1).** Selecting a row another browser holds runs `ClairBrowserWindow::Take`: the holder starts a still if it shows the tab, then `MoveFamilyHere` detaches the tab and its Peek with `TabStripModel::DetachTabAtForInsertion` and inserts them here with `InsertDetachedTabAt`, so the page and its tab handle survive. `ClairPeeks::Release` takes the pair out of the holder's Peek table first, so the move neither orphans nor unlinks the Peek, and `ClairPeeks::Adopt` links it again here. `ClairSpaceTabs::BeginMove` and `EndMove` keep the tabs at their places in the Space's list and push their new `browserID`.
- **The still and its placeholder (D2).** The window that gave its tab away copies the page with `CopyFromSurface` (`ClairBrowserWindow::CopyPage`; a take the user starts waits for the copy, or 250 ms, since viz copies only a surface it still draws, and a close that shows such a tab next waits with it; `ClairTakeOptions` says how a take waits) and activates a placeholder: a new tab page marked in its `WebContents` user data (`ClairSpaceTabs::MarkPlaceholder`). It is the one exception to two `add-spaces` rules: `ClairSpaceTabs` lists it in no Space, and while it is active the window keeps the Space it shows. `ClairBrowser.stillTabID` and `stillImage` describe the still; `PageCardView`'s `StillView` (`clair.still`) draws it faded, at 60% over the window's background, as Arc does. The still ends when the window becomes key (it takes the tab back at once; as in Arc, the click that made it key doesn't reach the sidebar's rows), when the window that took the tab shows another tab and no window shows it (`GiveBackToStill`: the most recently active window with a still of it takes it back without becoming key), when another tab becomes active there, or when the still's tab closes (`StillTabClosed`: the placeholder joins the shown Space at the top and the command bar opens). While a still shows, Cmd+W and the tab commands treat the still's row as the active one. A placeholder carries no session tags, so after a relaunch it is an ordinary new tab page.
- **Choosing a tab across windows (D3).** `ShowSpace` prefers the tab last active in the Space here unless another window shows it, then the Space's most recently active row that no window shows. The came-from rule chooses among all the rows and takes the chosen tab; with no row to show, the window stays on its Space on a new tab page (`KeepEmptiedSpace`, see Profiles below). Closing a tab another window holds closes it there (`CloseTab` hands it to its holder), which picks its own next tab among the rows no other window shows, so it never takes the page the user is looking at. A take waiting for its page's copy is dropped when another tab becomes active in the window meanwhile (`CancelPendingTake`), and a second close of the same tab joins the take instead of closing at once.
- **Closing a window (D4).** When the user closes a window, by its close button (`WindowCloseRequested`) or File > Close Window (`IDC_CLOSE_WINDOW` in `ExecuteTabCommand`), its window group closes as one (`ClairWindowGroup::CloseByUser`): while another regular window is open, every tab of each member but the placeholder moves to that window's member for its profile (`HandTabsTo`), each Peek with its parent, a still of one of them elsewhere gets it back, and the emptied browsers close without any leave-page prompt; their windows leave the screen at once and ignore becoming key meanwhile. Every other close, such as an extension's `chrome.windows.remove`, a profile closing or quitting, and the last regular window, incognito and guest windows, goes through Chromium's close flow (`Close`).

## Profiles

The `add-profiles` change's `design.md` (`openspec/changes/add-profiles/`) has the reasoning (D1–D13). A profile is a Chromium profile, and each Space uses one (`"profile"` in `clair.spaces`, the default profile when absent or gone). `ClairProfiles` lists, creates, renames and deletes profiles through `ProfileAttributesStorage` and `ProfileManager`, and pushes them to the host's observers. What Clair stores about a profile is an ID of its own (`add-tab-folders` D13): `clair.profiles` in Local State maps each lowercase UUID to the profile's directory on this Mac. `ClairProfiles` gives an ID to each profile without one at start (`ReconcileStoredIDs`, from `Start`) and when one is added, drops an entry when its profile is removed and at start when its directory is gone, and translates for the stores with `StoredIDOf` (a directory's ID, given if it has none) and `DirectoryOf`. `clair.spaces` and the favorites in `clair.pins` save the ID; everywhere else, `ClairHost.h` included, a profile is still its directory's name. Chromium's profile picker is off by default (`kBrowserProfilePickerAvailabilityOnStartup`), and its Profiles menu and "Warn Before Quitting" item leave the menu bar (`InstallNativeWindowMenus`).

The `native-quit-confirmation` change's `design.md` (`openspec/changes/archive/2026-11-15-native-quit-confirmation/`) has the reasoning (D1–D5) for the quit dialog. While "Warn before quitting" (`browser.confirm_to_quit`) is on, `engine/patches/clair/quit-confirmation.patch` has `-confirmQuitIfNeeded` call `clair::MaybeConfirmKeyboardQuit` for Cmd+Q (which Chromium runs as `IDC_EXIT`, never through the menu) and `-terminate:` call `clair::MaybeConfirmQuit` for a click on Clair › Quit Clair (`clair_native_layer.mm`). Both ask only with a native window open and no download in progress. `clair::ShowQuitConfirmation` (`clair_window_hooks.mm`) calls `-[ClairWindow showQuitConfirmation]` on the key or most recently active window, and ClairUI's `QuitConfirmation` answers through `-[ClairHost quitWithoutWarning]`. While ClairUI runs, Chromium's hold-to-quit panel never shows.

- **The group and its members (D3).** One Chromium `Browser` has one profile, so what the user sees as one window is a `ClairWindowGroup`: at most one browser per profile, each with its own `ClairBrowserWindow`, `ClairNativeWindow` and `ClairWindow`, one shown and the rest ordered out. A browser joins the group that creates it (`ClairWindowGroup::EnsureMember`), or else starts one; incognito and guest windows are groups of one.
- **The swap (D3).** Showing a Space of another profile (`ClairBrowserWindow::ShowSpace`, `ClairWindowGroup::ShowSpace`) finds or creates the member for its profile, which shows the Space; `SwapTo` gives it the group's frame, tells `ClairUI` (the bridge's `swappedInFrom:`, so the incoming window slides from the group's earlier Space and takes the outgoing window's sidebar and an open Manage Spaces), shows it and makes it key, and orders the old member out, in one run-loop turn without window animation. `Show()` or `Activate()` on a hidden member, as for a link from another app, switches the group to it.
- **The cover in full screen (D4).** While a member is in macOS full screen (the group's owner), the incoming member covers it as a `.fullScreenAuxiliary` child window at its frame, with no window controls (`ClairWindowGroup::Cover`), and full-screen requests go to the owner (`FullscreenNSWindow`). When the owner leaves full screen, the cover takes its frame and the owner is ordered out.
- **Hidden members (D5).** A hidden member shows no tab: taking a tab from it starts no still, and a swap away ends its still and drops a take it waited for (`Conceal`). It closes when its last real tab leaves (`MaybeCloseEmptyHiddenMember`).
- **The session tag and the restore setting (D6).** Each tab's session extra data also carries its window's group (`clair_window`), and `clair.windows` maps each group to the Space it shows. Session restore's windows don't show until it has finished (`ClairWindowGroup::HoldsShow`); then `ArrangeRestoredWindows` follows `ClairRestoreWindows`, the user default Settings › Advanced writes, read once at launch: on, each window comes back as its group, showing its Space; off, every restored browser joins the group of the window last active, and it shows `clair.last_space` on a new tab page. New tab pages and the windows they leave empty aren't restored (`DropNewTabPages`, beside `DropPeeks`).
- **Across profiles (D7–D9).** `openURL:inProfile:` and a window of a profile with no Space open in a Space of the right profile (`ClairWindowGroup::OpenInSpace`, `HandOverToLastSpace`). A tab can't change profile: changing a Space's profile, or moving a tab to a Space of another profile, reopens each tab at its URL in the group's member for the new profile and closes the original without its leave-page prompt (`ReopenInProfile` in `clair_space_tabs.mm`). The window follows its active tab when Move to Space moves it (`FollowActiveTab`).
- **The emptied Space (D13).** A close Clair starts on a Space's last row opens a new tab page there with the command bar instead of leaving the Space; closing that page while it is the Space's only row closes the window as the user's close does (`KeepEmptiedSpace`).

## Pins and favorites

The `add-pinned-tabs-and-favorites` change's `design.md` (`openspec/changes/add-pinned-tabs-and-favorites/`) has the reasoning (D1–D12).

- **The pin store (D1; `add-tab-folders` D1, D3).** `ClairPinStore` keeps every pinned tab, favorite and folder in Local State (`clair.pins`), one record each under `items`: a folder (`"kind": "folder"`) names its Space and its name; a pinned tab (`"kind": "pin"`) its Space and, in a folder, the folder; a favorite its profile, by the ID of `clair.profiles`; a pin also its URL, title and custom name. Each record carries its sort key, `order`, a fractional index from `clair_order_key.{h,mm}` (`OrderKeyBetween`: base-62 keys, "a0" first, between two neighbours or before the first or after the last), and a container's children are sorted by key, then by ID, so a move rewrites only the record that moved; a folder moving to another Space rewrites its pins' `space` too. The store keeps one index of children per container (`ChildrenOf`), rebuilt on load and on each write, and turns the contract's indices into keys between neighbours (`KeyAt`, which gives the whole container new keys only when two share one). Folders hold pinned tabs only, one level deep; on load, a pin whose folder is missing lists at its own Space's top level, and a record whose Space or profile is gone is dropped. Whether a folder is closed is this Mac's, apart from the records: `clair.closed_folders`. Icons are PNG files in `<user data dir>/Clair Pin Icons/`, written and read on a background sequence; at start-up it reads them and deletes those whose pin is gone. It remembers the last 25 pins and folders removed this session for Restore Last Closed Tab: a removed folder is one removal, with its pins and whether it was closed.
- **Pinned and favorited splits (`add-split-view` D10).** A split record (`"kind": "split"`) has the place a pin has, in a Space's pinned section, a folder or a profile's favorites, its sort key and its `ratio`; each of its two pins names it (`"split"`) and its pane (`"index"`, 0 or 1) instead of a place of its own, so moving the split rewrites only its record. A folder holds pins and splits, still one level deep. On load, a split without both its panes is dropped, its pins taking its place (`RepairSplits`). Removing either pin removes the split with both, as one removal for Restore Last Closed Tab; Separate Tabs (`SeparateSplit`) gives the leading pin the split's key and the trailing one the next; closing one pane of a shown pinned split takes its pin out (`TakeOutOfSplit`), the other keeping the split's place. `ClairHost.h` shows a split as a `ClairPinnedSplit` item, folders as lists of items, and the favorites as items too.
- **Binding (D2).** A tab showing a pin's page is bound to it: `ClairSpaceTabs::bound_` maps the pin to the tab, and the tab's tag carries the pin. A bound tab, and its Peek, are in no Today list; a pinned tab's Space is its pin's, and a favorite's tab has none, so the window keeps its Space while it shows one (`IntendedSpaceOf`). The pin's title and icon follow its tab only while the tab is at the pinned URL (its committed or originally requested URL, without the query and fragment). A Today tab's custom name is its tag's; a bound tab's is its pin's. The host pushes each Space's pinned items, pins and folders (`pinnedItemsDidChange:inSpace:`, with `ClairPinnedItem` and `ClairFolder` snapshots), and each profile's favorites (`favoritesDidChange:ofProfile:`), after the tab lists, once per run-loop turn.
- **The session tags (D2, D3).** `clair_pin` and `clair_name` ride beside `clair_space` and `clair_order` through the same three hooks of `space-session.patch`. A restored or reopened tab binds to its pin if the pin has no tab; otherwise it joins its Space's Today tabs.
- **Restore and removed pins (D3, D12).** `always-restore.patch` ends `SessionStartupPref::GetStartupPref` with `clair::ApplyStartupPref`, which makes it "continue where you left off" except in headless mode, and `chrome://settings` has no On startup section. Restore Last Closed Tab (`IDC_RESTORE_TAB`, run first by `ExecuteTabCommand`) puts back the newest removed pin or folder of the window's profile when that's newer than Chromium's newest recently closed entry, at its key, or at the end when its folder is gone or its key taken; a removed pin's tab closing carries `clair_pin`, so restoring that tab brings the pin back first, with its whole folder when the folder was deleted (`RestorePin`, `add-tab-folders` D7).
- **Opening, closing and moving (D4, D5).** `openPin:` activates the bound tab, or opens one bound to the pin; closing a bound tab leaves its pin unbound. Pinning, unpinning and moving between a Space's pinned tabs, the favorites and Today go through the host's and browser's pin calls; across profiles, the bound tab reopens bound to its pin (`ReopenInProfile`). Deleting a Space or removing a profile drops its pins and folders for good (D9).
- **Folders (`add-tab-folders` D2, D7, D8, D11).** The host's folder calls create, rename, open and close, move, duplicate and delete folders (`clair_native_layer.mm`); those that reach tabs are in `clair_space_tabs.mm`: `MoveFolder` moves the bound tabs as Move to Space does, `DeleteFolder` removes the folder first and then closes its tabs, `CloseTabsInFolder` closes them through the close flow, and `TurnFolderIntoSpace` creates a Space and moves the folder's pins into it with `MovePin`.
- **Peeks for other sites (D7).** `ClairPinnedLinkThrottle`, added to primary main frame navigations by `pinned-link-peek.patch`, turns a renderer-initiated link click with a gesture from a bound tab to another site (another scheme or host, as in Arc) into a Peek while the window's `opensPeekForOtherSites` is on. A URL entered from a favorite to another site opens a new Today tab (`LeavesFavorite`). A bound tab's Peek expands to the top of Today.
- **The title (D8).** `ClairBrowserWindow::UpdateTitleBar` uses the active row's custom name when it has one.
- **`ClairUI` (D11).** `SpacesModel` caches each Space's pins and each profile's favorites; `BrowserWindowModel` copies the shown Space's and the profile's, and its `allTabs` adds their tabs to the Today tabs. The sidebar shows the favorites grid (`FavoritesGrid`, laid out by `FavoritesLayout`) above the Space pager, and one list of pinned rows (`PinRow`, and `FolderRow` with its tabs indented under it, flattened by `PinsLogic.pinnedRows`), the divider with Clear (`TodayDivider`), "New Tab" and the Today rows, which drag between sections (`TabList`'s `onMove` and `onInsert`, `SidebarDragItem`; `PinsLogic.listDrop` maps a gap to a place, in a folder or at the top level). A folder's row takes drops on its middle through an AppKit view (`FolderDropArea`), as the favorites do. Right-clicking the sidebar outside the rows, or the "New Tab" row, opens the Space header's menu (`SpaceHeaderView.menuItems`): a catcher behind the page, the "New Tab" row's own, and the list's table view's menu (`TableMenuInstaller`). Renaming is in place (`RenameField`) or, for favorites, a dialog (`PinDialogs`). `PinsMenu` adds Pin Tab (Cmd+D), New Folder… (its dialog is in `PinDialogs`), Back to Pinned URL, Close and Keep Pinned and Clear Today (Shift+Cmd+K) to Chromium's Tab menu, hiding Chromium's own Pin Tab, and Collapse Pinned Tabs to the View menu. The collapse and the empty favorites box are user defaults (`PinsPreferences`), and the Links toggle is `ClairPeekForOtherSites`.

## Link rules

The `add-link-rules` change's `design.md` (`openspec/changes/archive/2026-11-15-add-link-rules/`) has the reasoning (D1–D7). Link rules send links from other apps to a Space, as Arc's Air Traffic Control and Dia's Link Rules do.

- **The store (D1).** `ClairLinkRuleStore` keeps the rules in order in Local State (`clair.link_rules`), each with an ID, a match (`contains`, `exact` or `prefix`), the text as typed, trimmed, and a Space. It keeps only valid rules: a known match, a text that reads as a URL, a Space that exists, and no repeat of an earlier rule's match and text. It observes `ClairSpaceStore` and drops a Space's rules when the Space goes, which also covers a profile removed with its Spaces; reading drops them too, in case Clair stopped in between.
- **The matcher (D3).** `ReadLinkRuleText` trims a text, rejects one that is empty or holds whitespace, puts `https://` in front when it has no `scheme://`, and requires a valid `http` or `https` URL with a host. `LinkRuleMatches` compares a link's spec without its fragment, and without its scheme when the rule's text had none, so `http` and `https` match alike: "URLs containing" looks for the raw text, ignoring case; "this exact URL" compares with the text read as a URL; "URLs starting with" checks that the link starts with it, so `example.com` becomes `example.com/` and doesn't match `example.com.evil.net`. The first matching rule wins (`FirstMatch`).
- **The hook (D2).** Launch Services (`-application:openURLs:`) and Handoff (`-application:continueUserActivity:restorationHandler:`) both send links through `-[AppController openStartupTabsReplacingNTP:]`, which queues them until start-up completes. `engine/patches/clair/link-rules.patch` calls `clair::RouteLinksFromOtherApps` there, just before `OpenStartupTabsInBrowser`: each link a rule matches opens through `ClairWindowGroup::OpenInSpace` and leaves the list, and Chromium opens the rest as it would. Links opened inside Clair never pass through it.
- **The contract (D4).** `-[ClairHost linkRules]` returns snapshots (`ClairChromiumLinkRule`), `-replaceLinkRules:` replaces them all through the store, and `-isValidLinkRuleText:` asks `ReadLinkRuleText`, so the dialog's error matches what the store keeps. There is no observer: only the dialog reads the rules, when it opens.
- **The dialog (D5–D7).** Settings › Links ends with a card, "Choose where links open inside Clair", after a divider, whose "Link Rules…" button (`SettingsWindowController.showLinkRules()`) shows `LinkRulesDialog` on the Settings window's `ClairDialogPresenter`: a 640 pt `ClairDialog` page (`ClairDialogPage.width`) with the rows as its content, "Add Rule" as its leading button, and Cancel and Done. `LinkRulesState` holds the rows until Done, which drops empty rows and checks the rest in order (valid text, an existing Space, no repeats) before `replaceLinkRules:`. Cancel with unsaved edits turns into a red "Discard Changes" (`ClairDialogButton.isDestructive` on a cancelling button), which closes on a second press. The rows' Space popups read `SpacesModel`, so a Space deleted while the dialog is open shows "Choose a Space".

## The toolbar

The browser controls show in one of two places, chosen by the `ClairShowsToolbar` preference (`ToolbarPreference`, on by default): a toolbar across the top of the card, or the sidebar's top row and URL field. The `add-page-toolbar` change's `design.md` (D1–D9) has the reasoning.

- **One rule decides where the controls show (D1).** `PageHeaderPolicy` takes the preference and the window's pane count, always 1 for now. Each pane shows a header while the preference is on or there's more than one pane, and the sidebar shows its controls only while no pane shows one. `BrowserWindowModel` exposes the result as `showsPageHeader` and `sidebarShowsControls`, and views read only those two. Split view will change the pane count and nothing else.
- **The toolbar is a page header inside the card (D2).** `PageToolbar`, a SwiftUI view, sits in `PageCardView`'s container at the top of the card, with a 1 pt line over the page's top row. The page, the still, infobars, DevTools and the drag strip lie below it. `PageCardView.contentTop` gives that offset, and find and the notice popup are placed from it (D7). Page full screen hides the toolbar.
- **A Peek covers it (D3).** Being in the container, the toolbar shrinks and washes with the parent page, and the click catcher closes the Peek. The Peek has its own `PageToolbar` with `.peek` content: back, forward, reload and the host, acting on the Peek's page.
- **The same controls, moved (D4).** The toolbar reuses the sidebar's buttons and identifiers (`clair.hideSidebar`, `clair.back`, `clair.forward`, `clair.reload`, `clair.urlField`, `clair.copyURL`, `clair.siteControls`, `clair.extensionAction`). The toolbar is `clair.toolbar` and the Peek's `clair.peekToolbar`. `ToolbarArrangement` places them: Arc's leading slots, a 36 pt trailing pitch, the host centred on the card, and, in a narrow card, extensions and then reload with the link icon left out before the host truncates. `ToolbarLayout` lays them out from it. Every toolbar button is an `IconButton` at Arc's 32 × 24 (`IconButtonSize.toolbarHeight`), the link icon 22 × 24, with Arc's glyph sizes (`IconButtonSize.toolbarGlyph` and the other `toolbar…Glyph` sizes: 14 pt for the toggle, back, forward and reload, smaller than the sidebar's 16, and 12 for the link); a pinned extension is a `ToolbarExtensionButton`, which wraps one with the extension's menu, badge and anchor. The toolbar's blank areas move and zoom the window through `TitleBarArea`, whatever the page-top drag setting.
- **Bubbles attach below the toolbar's controls (D6).** The toolbar reports its controls' frames in its own coordinate space, kept apart from the sidebar's, and `AnchorResolver` returns `.bottom` anchors for them while the toolbar shows and no page is in full screen. Extension popups open at the card's top-trailing corner, 40 pt in, whichever tile opened them (`ExtensionPopupWindow.Placement.topTrailing`).
- **Three ways to change it (D8, D9).** View › Hide Toolbar (⇧⌘D, `ToolbarMenuTarget`, added after the engine's Hide Sidebar once `NativeLayer` has started), the toolbar's context menu and the sidebar URL field's "Show as Toolbar", and the "Location bar" row on Settings › General (`LocationBarPicker`, with drawn `LayoutThumbnail`s). Every window observes the preference through `UserDefaults.didChangeNotification`.

## Bookmarks

The archived `add-bookmarks-menu` change's `design.md` (`openspec/changes/archive/2026-11-22-add-bookmarks-menu/`) has the reasoning (D1–D9). Clair has one bookmark list, Chromium's Other Bookmarks, which its interface calls "Bookmarks". `chrome://bookmarks` stays the manager.

- **The Bookmarks menu (D1, D7).** Chromium's menu and `BookmarkMenuBridge` stay. `InstallNativeWindowMenus` shows the menu, drops Chromium's two separators tagged `IDC_BOOKMARK_THIS_TAB`, and moves that item first, on Shift+Cmd+B; Bookmark All Tabs, Always Show Bookmarks Bar and the bookmarks side panel stay removed (`ClairIsRemovedCommand`). `MainMenuTitles` retitles `IDC_SHOW_BOOKMARK_MANAGER` "Manage Bookmarks" (Option+Cmd+B), and `ExecuteCommand` runs it as `clair::ShowBookmarkManager`, which opens `chrome://bookmarks` on Other Bookmarks rather than the empty Bookmarks Bar. `engine/patches/clair/bookmarks-menu-root.patch` makes `BookmarkMenuBridge::BuildRootMenu` list Other Bookmarks' contents directly, with no Bookmarks Bar or Other Bookmarks submenu, after one separator; it's a patch because the menu is built from the bridge's private members.
- **Bookmark This Page… and Edit Bookmark… (D2, D4).** `ClairWindowCommandHandler` titles the item from `clair::IsActivePageBookmarked` each time AppKit validates it. The native window's `ExecuteCommand` runs `IDC_BOOKMARK_THIS_TAB` itself (`clair::BookmarkActivePage`): it adds the page Chromium would bookmark (`chrome::GetURLAndTitleToBookmark`) at the end of Other Bookmarks, unless the user has bookmarked it, and calls `-[ClairWindow showBookmarkDialog:]` with a `ClairBookmark` snapshot whose `isNew` says which. Chromium's bookmark bubble never shows.
- **The contract (D3).** `ClairBrowser.bookmarkFolders` lists Other Bookmarks and its folders depth-first, and `-updateBookmark:title:folder:`, `-removeBookmark:` and `-addBookmarkFolder:` edit them (`clair_bookmarks.mm`). An incognito or guest window uses its original profile's bookmarks, as `BookmarkModelFactory` does.
- **The dialog (D5).** `BookmarkDialog` is a `ClairDialog` page: Name and Folder rows as its content, Remove as its leading button and Done, which Return and Esc press. The Folder popup is an `NSPopUpButton` (`BookmarkFolderPopup`), for the menu's indentation and checkmark; New Folder… swaps it for a field whose Return adds a folder, and Manage Bookmarks saves, closes and performs the main menu's Manage Bookmarks item. `BookmarkDialogState` saves through the browser however the dialog closes, except after Remove.
- **One list, and the notice (D6).** `ClairBookmarkBarDrain`, one per original profile (the profile's user data), started by `ClairBrowserWindow` for each window, keeps the Bookmarks Bar empty: when the bookmarks load, when a node lands directly in the bar, and when an import's extensive changes end, it moves the bar's children to the top of Other Bookmarks, in order, in a task of its own. The first drain that moves something asks the profile's most recently active normal window, or the first one to open, to show `BookmarksBarNotice`, and sets the Local State pref `clair.bookmarks_bar_notice_shown`, so it shows once for the whole app.
- **Suggestions (D8).** `ClairChromiumAutocomplete` runs every omnibox provider, bookmarks included, and shows a match's title first when Chromium marks it `swap_contents_and_description`, as the omnibox does. A row for a bookmarked page that isn't a search or an open tab is `ClairSuggestionKindBookmark`, with no icon, so `SuggestionRow` draws the `bookmark` symbol and VoiceOver reads "Bookmark".

## Split view

The `add-split-view` change's `design.md` (`openspec/changes/add-split-view/`) has the reasoning (D1–D13). A split is Chromium's own: two adjacent tabs of a `TabStripModel` in a split collection, with its `SplitTabId`, its ratio, and its pane order as the tabs' order. Session restore and tab restore keep splits without help.

- **`ClairSplits` (D1, D4, D5, D12).** One per native window, beside `ClairPeeks`, in `clair_splits.{h,mm}`. It makes splits from two tabs (`Make`, after `ClairBrowserWindow::BringHere` has brought both into the window), from a tab and a new tab page (`MakeWithNewTab`), replaces a pane (`Replace`: Chromium's `kReplace` closes the replaced tab, so it ends the split and restores it with the same ID), swaps, separates and resizes, and observes `OnSplitTabChanged` to push the change to `ClairSpaceTabs` and `ClairPeeks`. A `FocusWatcher` on each pane activates it when its contents take focus, so a click in the other pane focuses it; the active tab's partner is marked visible with it (`UpdateVisibility`). When a pane closes, the other is activated. A split Chromium makes itself, as Open Link in Split View does, gets the clicked tab back in the leading pane (`LeadWith`), except while a session restores.
- **Rows and commands.** A split is one row: `ClairBrowserWindow::RowOf` maps a pane to the split's row tab, the leading pane in Today, the tab commands (Ctrl+Tab, Cmd+1…9, Close Tabs Below) count it once, and `ActivateRow` shows the pane focused last (`LastFocusedPane`). Cmd+W and a pane's × close one pane (`CloseTab`); the row's × closes both through `ExecuteCloseTabsCommand`, so tab restore records one split entry.
- **Peeks (D3, D11).** A pane's Peek sits after the whole split in the strip, since a tab inserted inside a split ends it (`ClairPeeks::PeekIndexFor`); focusing the other pane closes it. Open in Split View expands the Peek and splits it with its parent (`OpenPeekInSplit`).
- **Option+click (D6).** `split-on-option-click.patch` makes Option without Shift give `NEW_SPLIT_VIEW` in Blink's `NavigationPolicyFromEventModifiers` and `ui::DispositionFromClick`, so a link isn't downloaded. `clair::MaybeOpenLink` (`clair_window_hooks.mm`, formerly `MaybeOpenPeek`) hands it to `ClairSplits::OpenLink`: a new background tab after the source and a split with it on a single page, the other pane on a split, the Peek itself in a Peek. The page's context menu keeps Chromium's Open Link in Split View.
- **Across windows and Spaces (D7).** `ClairSpaceTabs` keeps a split's tabs together in the Space's list (`KeepSplitsTogether`, run for every changed list), and Move to Space moves both. Taking a split's row from another window moves the split collection whole (`MoveFamilyHere`, with `DetachSplitTabForInsertion` and `InsertDetachedSplitTabAt`), its Peeks with it.
- **Pins (D10).** `clair::PinTab` pins a split as one item (`PinSplit`), and `OpenPin` on either of its pins opens the closed pages and shows them as a split with the saved ratio (`ShowPinnedSplit`). A restored split whose two tabs bind to one pinned split's pins is made again (`JoinPinnedSplit`). A ratio change of a pinned split is saved (`KeepPinnedRatio`).
- **`ClairUI` (D2, D3, D8, D9, D13).** `ClairTab` carries `splitPartnerID`, `isLeadingPane` and `splitRatio`; `TabListLogic.rows` folds the trailing pane into its leading pane's row, and `SplitLogic.shownSplit` gives the model's `shownSplit` (and `paneCount`). `BrowserRootView` lays out two `PageCardView`s with `SplitDividerView` between them, `PageDropView` over the page takes tabs dragged from the sidebar, and the overlays follow the focused pane. `PageToolbar` shows pane headers (`PageHeaderContent.pane`) and the split button (`SplitButton`), the sidebar shows `SplitRow` and the favorites `FavoriteSplitTile`, and `SplitMenu` adds Tabs › Split with Tab › and View › Add Split View (⌃⇧=), Close Split Pane (⌃⇧−) and Separate Tabs. The link status names a split or a Peek while Option or Shift is held (`SplitLogic.linkStatus`).

## Working on it

- **`ClairUI` only:** `scripts/run-local.sh` packages the checkout's `ClairUI` with the published engine and opens it with a throwaway profile (see `docs/building.md`). Unit tests use `FakeBrowser`, so most window logic can be tested without an engine.
- **Overlay or patch changes:** they change the engine key, so they need an engine build (`gh workflow run engine.yml -f ref=<branch>`). Before pushing, read the Chromium code you're calling in the runner's workspace (read only), and keep the overlay compiling by checking it against that tree's headers.

## Adding a hook

Chromium code that assumes a Views `BrowserView` crashes or does nothing for a native window. When a surface fails:

1. Find the call site in Chromium's source and the smallest place to branch: usually where it looks up the `BrowserView`, a Views widget or a `BrowserWindowFeatures` controller that a native window doesn't create.
2. Put the behaviour in the overlay: a function in `clair_window_hooks.{h,mm}` (or a new overlay file), which does nothing for Chromium's own windows (`clair::IsNativeWindow(browser)` or `clair::IsInNativeWindow(view)`), so the bare engine behaves as Chromium.
3. Add a hunk to `engine/patches/clair/native-window-hook.patch` that calls it, made against `build/base` in the runner's workspace (after ungoogled-chromium's patches, before Clair's), with any earlier Clair patch to the same file applied first. Clair's series applies with no fuzz.
4. Explain the hunk in the patch header, with what failed without it, and add a row to D13's table in the design.
5. Add any new overlay source to the `BUILD.gn` hunk for its directory, then build the engine and check the surface on the packaged app.
